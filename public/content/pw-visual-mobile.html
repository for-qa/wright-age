🎯 What is it?

Visual & Mobile Testing

Imagine inspecting a store window display: the door opens (functional test passes), but the "SALE" sign covers the price tag (visual bug). Shoppers leave without buying.

toHaveScreenshot() compares today's page to a saved baseline image. Combined with device emulation, you catch layout breaks on phones, tablets, and desktops before users do.

⚠️ The Pain

Why Visual Testing Matters for E-Commerce

A CSS change breaks the "Add to Cart" button layout. Functional tests pass — the button still clicks — but:

  • Button overlaps the price
  • Mobile users can't see it
  • Conversion drops 15%

Visual testing catches these regressions before production.

💻 Code Example

Screenshot Comparison Testing

First run creates a baseline in *-snapshots/. Later runs pixel-compare against it — like proofreading a printed catalog against the approved design.

test('product page visual test', async ({ page }) => {
  await page.goto('/products/wireless-headphones');
  await expect(page.getByRole('heading', { level: 1 })).toBeVisible();

  await expect(page).toHaveScreenshot('product-page.png');
});
🛒 Real-Life Example

Element-Level Screenshots

Capture just the product card or cart summary — smaller baselines, faster diffs, focused on the component that matters.

const productCard = page.getByTestId('product-card').first();
await expect(productCard).toHaveScreenshot('product-card.png');

await page.goto('/cart');
const summary = page.getByTestId('cart-summary');
await expect(summary).toHaveScreenshot('cart-summary.png');
📋 Reference

Screenshot Options

await expect(page).toHaveScreenshot('products-page.png', {
  fullPage: true,           // Entire scrollable page
  maxDiffPixels: 100,       // Allow 100 pixels to differ
  maxDiffPixelRatio: 0.02,  // Or 2% tolerance
  threshold: 0.3,             // Per-pixel color threshold (0-1)
});
💻 Code Example

Handling Dynamic Content

Stock counts, review totals, and timestamps change every run — mask them like putting sticky notes over moving parts of a photo.

await expect(page).toHaveScreenshot('product-detail.png', {
  mask: [
    page.getByTestId('stock-count'),
    page.getByTestId('review-count'),
    page.locator('.timestamp'),
  ],
});

// Wait for lazy-loaded images
await page.waitForFunction(() => {
  const images = document.querySelectorAll('img');
  return Array.from(images).every(img => img.complete);
});

📱 Real-Life Example

Mobile Device Emulation

Playwright ships 100+ device profiles — viewport, user agent, touch, and scale factor preconfigured.

import { test, devices } from '@playwright/test';

test.use({ ...devices['iPhone 13'] });

test('mobile product page', async ({ page }) => {
  await page.goto('/products/laptop');
  // Viewport 390×844, Safari UA, touch enabled
  await expect(page.getByRole('button', { name: 'Add to Cart' })).toBeVisible();
});

// playwright.config.ts — run same tests on many devices
projects: [
  { name: 'Desktop Chrome', use: { ...devices['Desktop Chrome'] } },
  { name: 'Mobile Safari', use: { ...devices['iPhone 13'] } },
  { name: 'iPad', use: { ...devices['iPad Pro 11'] } },
]

Mobile Checkout

Touch targets should be at least 44×44px — Apple's recommended minimum for fingers, not mouse cursors.

const emailInput = page.getByLabel('Email');
const inputBox = await emailInput.boundingBox();
const viewport = page.viewportSize();
expect(inputBox?.width).toBeGreaterThan((viewport?.width || 0) * 0.8);

const payButton = page.getByRole('button', { name: 'Pay Now' });
const box = await payButton.boundingBox();
expect(box?.height).toBeGreaterThanOrEqual(44);
expect(box?.width).toBeGreaterThanOrEqual(44);
📐 Real-Life Example

Responsive Design Testing

const breakpoints = [
  { name: 'mobile', width: 375, height: 667 },
  { name: 'tablet', width: 768, height: 1024 },
  { name: 'desktop', width: 1280, height: 800 },
];

for (const bp of breakpoints) {
  test(`product grid at ${bp.name}`, async ({ page }) => {
    await page.setViewportSize({ width: bp.width, height: bp.height });
    await page.goto('/products');
    await expect(page).toHaveScreenshot(`product-grid-${bp.name}.png`);
  });
}

// Or verify CSS grid columns programmatically
await page.setViewportSize({ width: 1280, height: 800 });
let cols = await grid.evaluate(el => getComputedStyle(el).gridTemplateColumns.split(' ').length);
expect(cols).toBe(4);  // desktop: 4 columns
🐳 CI

Visual Testing in CI

Different OSes render fonts and anti-aliasing differently — run visual tests in a Docker Playwright image for consistent baselines.

// playwright.config.ts
expect: {
  toHaveScreenshot: {
    maxDiffPixelRatio: 0.05,
    animations: 'disabled',
    caret: 'hide',
  },
},

// Snapshots are per-platform by default:
// product-page-chromium-linux.png vs product-page-chromium-darwin.png

// Docker: mcr.microsoft.com/playwright:v1.40.0-jammy
docker run --rm -v $(pwd):/app -w /app mcr.microsoft.com/playwright:v1.40.0-jammy npx playwright test
⚠️ Watch Out!

Common Mistakes

  • ❌ Screenshot before content loads: Comparing half-loaded pages.
    ✅ Wait for headings, images, spinners hidden before toHaveScreenshot.
  • ❌ No masking on dynamic counters: "Only 5 left!" fails every run.
    ✅ Mask stock, timestamps, ads or freeze animations.
  • ❌ Updating baselines on Mac, running CI on Linux: Font rendering diffs flood failures.
    ✅ Generate baselines in Docker — same image as CI.
  • ❌ Only desktop visual tests for a mobile-first shop: Hamburger menu bugs slip through.
    ✅ Projects per device — iPhone, Pixel, iPad at minimum.
📝 Summary

Key Takeaways

  • toHaveScreenshot() compares against baseline images
  • Mask dynamic content — timestamps, counters, ads
  • 100+ device profiles built into Playwright
  • Test breakpoints systematically for responsive design
  • Mobile UX — touch targets, hamburger menus, sticky CTAs
  • Docker in CI for consistent screenshot rendering
