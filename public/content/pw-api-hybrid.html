API Testing & Hybrid

Here's a secret: the fastest UI test is one that doesn't use the UI when it doesn't have to. Playwright's API layer lets you skip slow setup and teardown.

🎯 What is it?

API Testing & Hybrid Workflows

Imagine moving into a furnished apartment: you wouldn't build every piece of furniture from scratch just to test the light switch. For e-commerce tests, API calls furnish the cart and user session; the UI verifies what users actually see on the confirmation page.

Playwright's { request } fixture sends HTTP calls in the same test run as your browser — same cookies, same auth context when configured.

⚡ Real-Life Example

The Speed Problem

A full UI checkout might take ~13 seconds — homepage, search, product page, cart, form, submit. If you only care about the confirmation screen, the first six steps are just setup.

Approach Steps ~Time
Pure UI checkoutBrowse → cart → form → submit → verify~13s
Hybrid API + UIAPI cart → goto checkout → submit (UI) → verify~4.2s (3× faster)

Playwright Request Context

The request fixture is your direct line to the backend — no browser rendering required.

test('fetch products via API', async ({ request }) => {
  const response = await request.get('https://api.shop.example/products');

  expect(response.ok()).toBeTruthy();
  expect(response.status()).toBe(200);

  const products = await response.json();
  expect(products.length).toBeGreaterThan(0);
  expect(products[0]).toHaveProperty('name');
  expect(products[0]).toHaveProperty('price');
});

API-Based Authentication

Logging in through the UI in beforeEach costs 3–5 seconds per test — like showing ID at every store aisle instead of once at the door.

❌
Slow: UI login every test
test.beforeEach(async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('user@example.com');
  await page.getByLabel('Password').fill('password123');
  await page.getByRole('button', { name: 'Login' }).click();
  // 3-5 seconds × 100 tests = painful
});
💻 Code Example

Solution 1: API Login + storageState

Log in once via API, save cookies/localStorage, reuse in every test — show ID once at the door.

// auth.setup.ts
const authFile = 'playwright/.auth/user.json';

setup('authenticate', async ({ request }) => {
  const response = await request.post('/api/auth/login', {
    data: { email: 'user@example.com', password: 'password123' },
  });
  expect(response.ok()).toBeTruthy();
  await request.storageState({ path: authFile });
});

// playwright.config.ts
projects: [
  { name: 'setup', testMatch: /.*\.setup\.ts/ },
  {
    name: 'chromium',
    dependencies: ['setup'],
    use: { storageState: 'playwright/.auth/user.json' },
  },
]

Solution 2: Fixture-Based Auth

Custom fixtures expose authToken and an authenticatedRequest with Bearer headers baked in.

export const test = base.extend<AuthFixture>({
  authToken: async ({ request }, use) => {
    const response = await request.post('/api/auth/login', {
      data: {
        email: process.env.TEST_USER_EMAIL,
        password: process.env.TEST_USER_PASSWORD,
      },
    });
    const { token } = await response.json();
    await use(token);
  },

  authenticatedRequest: async ({ playwright, authToken }, use) => {
    const context = await playwright.request.newContext({
      extraHTTPHeaders: { 'Authorization': `Bearer ${authToken}` },
    });
    await use(context);
    await context.dispose();
  },
});

await page.goto('/checkout');
await expect(page.getByTestId('cart-item')).toHaveCount(2);
3
API cleanup after UI test
// UI: complete checkout (what we're testing)
const orderId = await page.getByTestId('order-id').textContent();

// API: cancel / refund test order
await request.post(`/api/orders/${orderId}/cancel`, {
  data: { reason: 'Test cleanup' },
});
🏭 Code Example

Test Data Factory

A factory is a backstage crew — creates users, products, and orders via API, then tears them down so tests stay isolated.

export class TestDataFactory {
  constructor(private request: APIRequestContext) {}

  async createProduct(data?: Partial<ProductData>): Promise<string> {
    const response = await this.request.post('/api/products', {
      data: { name: `Test Product ${Date.now()}`, price: 29.99, stock: 100, ...data },
    });
    const { productId } = await response.json();
    return productId;
  }

  async cleanup(resource: string, id: string): Promise<void> {
    await this.request.delete(`/api/${resource}/${id}`);
  }
}

// In test:
const productId = await factory.createProduct({ name: 'Test Widget', price: 19.99 });
await page.goto(`/products/${productId}`);
await factory.cleanup('products', productId);

API Response Validation

Schema checks — required fields, types, sane values. Contract tests — shape of cart JSON without opening a browser.

const product = await response.json();
expect(typeof product.price).toBe('number');
expect(product.price).toBeGreaterThan(0);

// Contract
const cart = await (await request.get('/api/cart')).json();
expect(cart).toMatchObject({
  items: expect.any(Array),
  subtotal: expect.any(Number),
  tax: expect.any(Number),
  total: expect.any(Number),
});

⚠️ Watch Out!

Common Mistakes

  • ❌ Hybrid everything: Using API for the entire checkout when the test goal is "user can complete purchase."
    ✅ API only for setup/teardown — UI for the behavior under test.
  • ❌ Skipping cleanup: API-created orders pile up in staging.
    ✅ Cancel/delete via API in afterEach or factory cleanup().
  • ❌ UI login in every test when API auth + storageState exists.
    ✅ One setup project or auth fixture — reuse session.
  • ❌ Assuming API and UI share state without cookies: Cart API may need same session as browser.
    ✅ Use shared storageState or ensure request inherits cookies from context.
📝 Summary

Key Takeaways

  • request fixture — API calls in the same test context
  • API auth + storageState — massive login time savings
  • Hybrid — fast API setup + UI verification of what users see
  • Test data factories — isolated, repeatable data
  • API cleanup — keep staging environments clean
  • Contract testing — validate API shape without UI
